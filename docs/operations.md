# 运营与质量提升方案（江西银行业版）

面向维护者。技能在用户本地运行、不回传任何数据，所以运营靠三件事：**可复用的质量关卡**、**用户主动反馈的坏案例闭环**、**发布前的固定评测**。

## 1. 定位

**一句话**：给在江西展业的银行员工，按自己的岗位和关注池，每天/每周看可追溯的江西政企公开动态。

| 用户 | 典型需求 | 对应能力 |
|---|---|---|
| 分行管理层 | 全省及辖内政策、重大项目、例外事项 | 行领导视角、要报版 |
| 公司金融、战略客户、投行 | 重点企业与项目节点、募资与重组公告 | 关注池、项目追踪专题 |
| 科技、绿色、普惠、涉农金融 | 名单公示、申报窗口、环评与技改项目 | 条线视角与岗位画像 |
| 风险、授信审批、内控合规 | 审批阶段、废标、处罚与口径反证 | 风险类视角、证据门 |
| 一线客户经理 | 关注池对象下一步公开文件 | 速读版晨报、关注池动态 |

差异化：每条事实可追到原文；按岗位与关注池聚焦；关注池强制公开研究边界，不碰行内客户数据。运营上守住这一点，不为“更贴近业务”放松隐私边界或加入营销推断。

## 2. 三道质量关卡

| 关卡 | 工具 | 拦截什么 | 维护方式 |
|---|---|---|---|
| 结构 | `validate-config`、`render`内置校验 | 时间窗、引用ID、URL安全、正式稿缺口 | 每个坏案例若属结构问题，补一个单元测试 |
| 内容 | `lint` | 条数式摘要、读者正文夹带编制说明、信贷营销与投资建议措辞、渲染性用词、分类缺失、主题过碎 | 坏案例若可用规则识别，补到 `briefing_tool.py` 的词表或规则，并在 `references/writing-style.md` 加正反例 |
| 行为 | `evals/` | 岗位映射错、关注池收录内部信息、省外请求未拒绝、擅自导出或发送 | 坏案例若属流程判断，补一条eval |

**北极星质量指标：事实差错率** = 用户反馈的错误事实条数 ÷ 交付事实条数。其余为过程指标：

| 指标 | 计算 | 来源 |
|---|---|---|
| 一手核实率 | primary_verified ÷ 全部事项 | 04-final.json |
| 覆盖完整率 | available_days ÷ expected_days；覆盖矩阵已完成格 ÷ 计划格 | RUN-STATE.json |
| 观察稿占比 | 观察稿期数 ÷ 总期数 | 运行目录 |
| lint分数 | `lint` 输出的score，error应为0 | 运行目录 |
| 速览返工率 | 用户要求改写速览的次数 ÷ 期数 | 用户反馈 |

建议在 `RUN-STATE.json` 增加 `quality` 对象，记录 lint_score、primary_ratio、coverage_ratio、pending_count 和 observation_reasons。这些数据只留在用户本地；用户愿意时可脱敏后随反馈提交。

## 3. 坏案例闭环

1. **收集**：GitHub Issue 模板“质量反馈”“地区与信源补充”；SkillHub评论区；用户直接提供的脱敏运行目录。不接收内部客户数据、凭证或非公开材料，收到后立即删除并提醒用户。
2. **归类**：采集遗漏 / 核验错误 / 口径错误 / 写作问题 / 模板与图表 / 触发与流程。
3. **转成回归**：结构→单元测试；写作→lint规则+写作规范示例；流程→eval用例；模板→渲染测试和截图核对。
4. **修复与记录**：在 `CHANGELOG.md` 写明“修复了哪类坏案例”，在Issue回复对应版本。
5. **复盘**：每月统计各类坏案例数量，数量最多的一类作为下月重点。

原则：每个被确认的坏案例都要留下一个能自动发现它的检查，避免同类问题再出现。

## 4. 评测集

- `evals/evals.json`：行为评测，覆盖默认江西全省、岗位映射、自定义岗位、关注池建立与CSV导入、拒绝内部客户名单、省外请求、关注池专题、拒绝营销推断等。每条有可逐项判定的 expectations。
- `evals/trigger-evals.json`：触发评测，应触发与不应触发的请求各半，用于调整 `SKILL.md` 的 description。
- **黄金回放样本**：每季度挑2–3个历史日期，用真实公开原文做回放简报（参照 `examples/report-public-replay.json`），固定为回归样本。新版本重跑后，内容差异必须能解释。

发版前跑一遍评测，记录通过率；通过率下降不发版。

## 5. 内容资产共建

| 资产 | 现状 | 下一步 |
|---|---|---|
| 江西信源地图 | `references/source-map.md` 列省级机构与检索式 | 补11个设区市信源卡片：官网、环评公示、公共资源交易入口，每张卡写核验日期 |
| 关注池模板 | `examples/pool-template.csv` | 按条线提供示例关注池（只含公开上市公司、园区与政策） |
| 主题与阶段词表 | `references/writing-style.md` | 根据坏案例和高频新主题每季度修订一次，保持跨期可比 |
| 阅读视角 | 5组30余种 | 新视角须写明优先展开、明确不展示、推荐版式，并同步代码与测试 |
| 模板 | 4配色×3版式 | 新配色须通过图表色觉校验（全两两配对）和正文对比度≥4.5:1；新版式须通过宽窄屏无横向溢出检查 |

贡献规则：信源只收官方或正式披露渠道；不收内部系统、付费数据库账号或需要绕过访问控制的入口。

## 6. 版本节奏

- 版本号：主版本 = 报告契约不兼容或默认行为改变（如关注池字段不兼容调整）；次版本 = 新增视角、模板、可选字段；修订号 = 修复。
- 节奏：修复随时发；次版本约每月一次；每季度一次回放复盘。
- 发版清单：
  - [ ] `python3 -B -m unittest discover -s tests` 全部通过
  - [ ] 所有 `examples/` 报告 `lint` 无error
  - [ ] evals 通过率不低于上一版
  - [ ] `SKILL.md` frontmatter 的 version 与 metadata.version、README版本一致
  - [ ] `CHANGELOG.md` 已更新
  - [ ] `skillhub publish . --dry-run` 预检通过（由仓库所有者执行发布）

## 7. 分发

- 本仓库默认私有。面向机构内推广时，由使用机构自行评估合规要求后决定发布渠道；公开发布前确认示例中没有任何机构客户关系信息。
- 推广物料按岗位准备：每个条线3条示例提示词、一份关注池CSV模板说明、一张速读版晨报截图。
- 与父技能保持同步：父技能的证据门、lint和模板修复每月合并一次（见第9节）。

## 8. 风险控制

- **版权**：简报只做事实摘要和原文链接，不整段转载。
- **负面信息**：处罚、违约等只采信一手正式文件，不传播传闻。
- **隐私**：不处理自然人信息；风险报道以法人主体和必要公开事实为限。
- **误用**：明确不提供授信审批、投资建议和营销线索；`lint` 对相关措辞报error。
- **品牌**：模板不带任何机构名称和标识，不支持在页面中加入机构品牌。

## 9. 与父技能同步与路线图

本仓库从 `regional-enterprise-briefing` 2.0.0 拆出。`scripts/report_design.py`、`assets/report.css` 的模板部分和 `lint` 规则应定期从父技能合并：先在父仓库修复并加测试，再把差异带到本仓库，跑全部测试后发版。江西与银行业特有的部分（地区校验、岗位视角、岗位画像、关注池、江西信源地图）只在本仓库维护。
